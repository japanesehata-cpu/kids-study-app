# 開発ガイドライン

前提：[architecture.md](./architecture.md)、[repository-structure.md](./repository-structure.md)。

## 1. 開発環境のセットアップ
```bash
npm install
npm run dev          # http://localhost:5173/kids-study-app/
```

素材を作り直すときだけ、以下も用意する（アプリの開発・テスト・ビルドには不要）。
- 画像：Apple Silicon の Mac で SDXL 系モデルを動かす Python 環境。キャラクターデザインを作るときだけ、`.env` に `GEMINI_API_KEY` を置く（`.env.example` を参照）。
- 音声：ローカルの VOICEVOX エンジン（ポート 50021）。英語は Kokoro／Piper のサーバー（`npm run tts-server` など）。

## 2. コーディング規約
- フォーマッタ／リンタ：リントは oxlint（`npm run lint`）。React Hooks の規則違反はエラーにする。フォーマッタは置かず、周りのコードの書き方（インデント2、シングルクォート、セミコロンなし）に合わせる。
- 型：TypeScript の strict と、未使用の変数・引数の禁止を守る。`any` は使わない。型だけの import は `import type` にする。
- 命名規則（変数・関数・型・定数）：
  - 変数・関数はキャメルケース（`generateQuestionSet`）、型・部品はパスカルケース（`CategoryProgress`）。
  - 変更しない設定値の定数は大文字のスネークケース（`SET_SIZE`、`CATEGORY_MAX_LEVEL`）。
  - ファイル名の規則は [repository-structure.md](./repository-structure.md#4-命名規則ファイルディレクトリ) を参照。
- 表示文字列：画面に出す文字は `src/i18n/dictionary.ts` に置き、日本語と英語の両方を書く。部品の中に文字を直接書かない。
- コメントの方針：コードを読めば分かる「何をしているか」は書かない。「なぜそうしたか」（子どもの使い方、端末の不具合への対策、却下した案）を書く。
- エラーハンドリングの方針：
  - 子どもの操作を止めない。保存データの読み込み失敗・音声の再生失敗・画像の読み込み失敗は、初期状態や代わりの手段に切り替えて先へ進める。
  - 画面の描画の例外はエラー境界で受け、ホームへ戻れるようにする。
  - localStorage や Web Audio などブラウザの機能は、使えない場合を想定して `lib/` の中で try/catch する。
  - 連続タップ・画面遷移中のタップで、回答や遷移が二重にならないようにする。

### 子ども向けの UI の規則
- **縦画面に特化する。** どの画面も、スマートフォンの縦画面でスクロールなしに1画面に収める（[PRD 6](./product-requirements.md#6-非機能要件)）。
- タップ対象は子どもの指で押せる大きさにする。
- 文字を読めなくても進められるよう、問題の大事な情報は音声と絵でも伝える。
- 不正解の表現（音・言葉・表情）で子どもを責めない、怖がらせない。
- 演出は短く（正解演出は約1.5秒以内）、操作を妨げない。端末の「視差効果を減らす」設定では大きな動きを止める。
- 色・角の丸み・影などは `src/styles/theme.css` の変数を使い、色を直接書かない。

### 学習内容の規則
- 1つのレベルは1つのはっきりした難しさにする。難しさの違う問題を1つのレベルに混ぜない。
- 漢字のヒントや例文は、その漢字自体を使った言葉にする（例：雨 → 「雨が ふる」）。同じ音の別の言葉（あめだま など）にしない。
- 読み上げで意味の違う言葉に聞こえないか確認する（例：「あめ」が「飴」に聞こえる）。必要なら漢字で書いて読み上げさせる。
- 物の絵は本物の形を正しく伝える。物に顔をつけたり、比率を変えたりしない（キャラクターと飾りの画像は別）。

### 素材の規則
- 画像生成は、キャラクターデザインだけ Gemini API を使い、それ以外はローカルの SDXL 系モデルで作る（[architecture.md](./architecture.md#6-外部サービス依存関係)）。画風は `scripts/image-style-guardrail.mjs` に従う。
- 生成した画像は、すべて元の画像と並べて目で確認し、使うものだけを `public/` に置く。採用しなかった候補は設定 JSON に `rejected` として残し、同じ失敗をくり返さない。
- 固定の読み上げ文を足したり変えたりしたら、事前の音声を作り直す（`npm run generate:tts-cache`）。足りない音声がないかは `scripts/audit-tts-cache.mjs` で確かめる。
- 漢字のデータを変えたら `node scripts/check-kanji-speech.mjs` で読み上げを確かめ、漢字の音声を作り直す。漢字を足したときは、なぞり書き用のフォントも取り直す（`node --experimental-strip-types scripts/fetch-handwriting-font.mjs`）。
- スクリプトが作るデータ（例：`src/domain/spotScenes.ts`）は手で書き換えない。
- まちがいさがしの背景の違いは、2つの方式のファイル名の id が重ならないようにする（`bg__d<N>` は方式 A 専用。方式 B の id を `d` で始めない）。

## 3. テスト方針
- テストの種類と対象（単体／結合／E2E）：
  - 単体テスト（中心）：`domain` の問題の生成・採点・レベルアップ・復習・重複回避と、出題範囲のデータの整合性（例：漢字のヒントにその漢字が入っている、正解が選択肢に入っている）。`lib` の純粋な処理（書き順の照合など）。
  - 部品のテスト：エラー境界など、壊れると子どもが先に進めなくなる部品。
  - E2E テストは置かない。画面の確認は下の「画面での確認」で行う。
- 配置場所と命名：対象と同じ階層の `__tests__/` に `<対象>.test.ts(x)`。
- 実行コマンド：`npm test`
- カバレッジの目安：数値の目標は置かない。新しいカテゴリ・レベル・出題範囲のデータを足したら、その生成とデータの整合性のテストを必ず足す。

### 画面での確認
- 画面に関わる変更は、ブラウザで実際に動かして確かめる。
- スマホの幅（320／375／430px）は、ページの中に固定幅の iframe を作って確かめる。**確認のためにブラウザのウィンドウの大きさを変えない。**
- iOS Safari 特有の動き（音の自動再生、スクロールの跳ね返り）に関わる変更は、実機でも確かめる。

## 4. Git 運用
- ブランチ戦略：`main` だけを使う（開発者1人のため）。`main` への push がそのまま本番の公開になる。
- ブランチ命名：該当なし（必要になったら `feature/<内容>` とする）。
- コミットとデプロイの手順：変更を作って確かめた後、開発者が「コミットしてデプロイして」と指示したときだけコミットし、`main` に push する。AI アシスタントが自分の判断でコミット・push しない。
- コミットメッセージ規約：日本語で、`<対象>: <変えたこと>` の形にする（例：`まちがいさがし: 背景のまちがいを各背景5個に増量`）。本文には理由や数を書く。
- プルリクエストのルール（レビュー・マージ条件）：該当なし（`main` に直接コミットする）。
- push の後は GitHub Actions の公開が成功したことを確かめる。

## 5. 品質チェック
コミット前に実行するコマンド：
```bash
npm run lint
npm test
npm run build        # 型チェック（tsc -b）とビルド
```

- リントはエラー0を必須とする。警告は新しく増やさない。
- テストとビルドはすべて成功していること。

## 6. ドキュメント更新ルール
- `docs/` の永続的ドキュメント6種がプロジェクトの北極星。実装と食い違ったらドキュメントが正。
- 仕様・設計を変えるときは、先にドキュメントを更新・承認してから実装を変える（同じコミットに含めてよい）。
- 機能を足したら [functional-design.md](./functional-design.md) と [glossary.md](./glossary.md)、技術を変えたら [architecture.md](./architecture.md)・[repository-structure.md](./repository-structure.md)・本書も見直す。

## 7. 禁止事項・注意点
- 実行時に外部へ通信する処理（アクセス解析、外部 API、広告）を入れない。
- 学習記録・個人情報を外部へ送らない。URL に入れない。
- `.env` や API キーをコミットしない。
- 公開版から localhost の音声エンジンへ問い合わせない（開発環境のときだけ）。
- 保存データの形を変えるときは、古い形のデータも読めるようにする（新しい項目は任意の項目にする）。読めない場合も起動を止めない。
- 漢字の問題の id（1年は `k1`〜`k80`、2年は `k2-N`）など、保存データや音声ファイル名に使われている id を変えない。
- ずけい（shapes）は品質が整うまでホームに出さない。
